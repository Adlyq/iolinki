## 1. Method and extracted data

The full Test Spec was converted with `pdftotext -layout` to `/tmp/testspec_10032.txt`; 313 case blocks were parsed into `/tmp/cases2.json`. The audit compares each `CHECKS` entry line-by-line against the Test Spec table (precondition, procedure, evaluation, test-passed).

The terminology used below:

- **exact** — all spec procedure steps are performed and the exact evaluation criteria are asserted.
- **partial** — correct scenario and some exact criteria, but at least one required step or assertion is absent.
- **shallow** — only a weak proxy is asserted (for example only `OK`/`ERR`, only a length, or no exception).
- **wrong-scenario** — the precondition/procedure is materially different from the Test Spec (wrong mode, wrong object, no interruption, no write, etc.). A pass does not exercise the specified case.
- **not-applicable** — the case is (or is claimed to be) outside the DUT scope, or the check is a skip stub.
- **blocked-oracle** — the required IODD/vendor reference values are missing.

`implementation` in the CSV means: `yes` = a real check function exists and is in `CHECKS`; `yes-skipped` = a check function exists but the CSV category prevents execution; `no` = only a skip stub.

## 4. Serious findings, with evidence

### 4.1 `SDCI_TC_0108` — tautological record check (shallow)

`check_0108` (`spec_checks.py:265-268`) is:

```python
for sub in range(1, 6):
    line = master.command(f"od get 0x0003 {sub}", timeout=15)
    assert "OK" in line or "ERR" in line, line
```

Every possible response passes. The Test Spec requires sub1 length 1 and value 0..5, sub2 length 1 with bits 0 and 3..6 zero, sub3 length 4 and value 0..2048, sub4 length 4, and sub5 length 2 + 3n (2..212). The check asserts none of this, so a `pass` proves only that the transport answered.

### 4.2 `SDCI_TC_0110` — never writes an invalid value (shallow)

`check_0110` (`spec_checks.py:259-262`) reads `0x000C`; if the read is `ERR` it skips, otherwise it returns. The spec procedure writes each reserved DeviceAccessLocks bit and requires `0x8030` plus read-back `0x0000`. The check performs no write at all, so it cannot detect reserved-bit acceptance.

### 4.3 `SDCI_TC_0060` — no 16-bit write (wrong-scenario)

`check_0060` (`spec_checks.py:206-207`) is literally `check_0059(master)`. `check_0059` reads reserved index `0x7F32` and accepts either `OK` or `ERR`. The spec requires a 16-bit ISDU **write** using Config2, a busy/response check, a read-back, and `temp == Config2` (or `Index not available`). The check performs no write and no read-back.

### 4.4 Event cases `0069`/`0070`/`0071`/`0074`/`0075`/`0076` — one injection helper replaces six scenarios (wrong-scenario)

All six are wrappers around `_event_check` (`spec_checks.py:432-458`), which writes one vendor hook `od set 0x00E1 0 <code> <type> 01` and waits for that code in `event get`. Consequences:

- `0070` requires EUT in **PREOPERATE** (`spec_checks.py:544-545`); `test_spec_all.py:117-192` leaves the fixture in OPERATE, so the case runs in the wrong mode.
- `0071` requires StatusCode 0x00/0xAA, disappear, re-appear and SCf write-back; the check only injects an Event and reads it.
- `0074` requires appear **and disappear** plus qualifier mode checks; no `EventA_Disappear` is sent.
- `0075` requires two overlapping events A/B and ordering checks; only one event is injected.
- `0076` requires appear+disappear inside 50 ms/2 MasterCycleTime; no disappear is sent.
- The Test Spec uses `Config7`; the HIL uses vendor test hook `0x00E1`, so it tests the event transport, not the specified application-level event injection.

### 4.5 `SDCI_TC_0072` — no communication interruption (wrong-scenario)

`check_0072` (`spec_checks.py:552-553`) calls `_event_check(0x8C00, 1)`. The spec requires: read EventQualifier/EventCode, reset the DTU, pause 2 s, wake the Device to OPERATE, then read/acknowledge until the Event is found and verify the stored qualifier/code. No reset or pause occurs. The pre-case `ensure_operate(force=True)` power cycle (`test_spec_all.py:214-217`) happens **before** the injection and therefore cannot test event persistence across an interruption.

### 4.6 `SDCI_TC_0073` — no power interruption (wrong-scenario)

`check_0073` (`spec_checks.py:556-557`) is again only `_event_check(0x8C00, 1)`. The spec requires a 15 s power-down/reconnect, wake-up, event read, and verification that Event A is not reported with mode `disappear`. None of that happens.

### 4.7 `SDCI_TC_0323` — incorrectly declared n/a (not-applicable due to wrong rationale)

`check_0323` (`spec_checks.py:943-944`) unconditionally runs `pytest.skip("DUT DS is enabled; no-DS case is N/A")`. But 0323 is `TCD_DLIC_DEFP_DSRECORDMARKER`, the DataStorageIndex **termination marker** case. Its spec precondition is `EUT: OPERATE`; it is not a no-DS case. The spec asks for sub3=0, sub5 length=2 and value=0. The case is applicable to a DS device and is silently removed from the matrix.

### 4.8 `SDCI_TC_0155`/`0316`/`0317`/`0318` — SystemCommand cases declared n/a without evidence

The report table marks all four as `n/a` (`"DUT 不支持..."`), so `test_spec_all.py:205-206` never calls their checks. The checks themselves are `_system_command` wrappers (`spec_checks.py:391-429`) that only send 0x82/0x80/0x81/0x83 and wait for OPERATE. They do not check events, startup count, DS flag, DID/RID, DeviceStatus, or parameter defaults. Cross-checking the device library shows these commands are implemented (`src/isdu.c:837-857`) and covered by unit tests (`tests/test_system_commands.c:54-70`), so the `n/a` classification is unproven. Even if it were true, the check bodies would not be conformance evidence.

### 4.9 `SDCI_TC_0063` — wrong object and wrong length (wrong-scenario)

`check_0063` (`spec_checks.py:221-224`) writes 33 bytes to ApplicationSpecificTag `0x0018` and asserts only `ERR`. The spec requires the Config1 writable object with 70 octets when 64 are permitted, ErrorType `Parameter length overrun` (0x8033), and `temp1 == temp2`. `0x0018` has a maximum of 32 octets (interface spec Table B.8), so this is not the specified 64-octet object; it duplicates 0123 and does not verify the value was unchanged.

### 4.10 `SDCI_TC_0157` — wrong object type (wrong-scenario)

`check_0157` (`spec_checks.py:620-625`) uses VendorName `0x0010`, sub0 `OK` and sub1 `ERR`. The spec precondition is a **complex data type** with `subindexAccessSupported = true`, and the procedure writes and reads sub0 and sub-n and compares all four values. VendorName is a string, not the required complex record; no write or consistency comparison is performed.

### 4.11 `SDCI_TC_0373` — only `OK` from DeviceStatus (shallow)

`check_0373` (`spec_checks.py:588-593`) injects an event, acknowledges it, reads `0x0024` with length 1 and asserts only `OK`. The spec requires DeviceStatus in 1..4, DetailedDeviceStatus containing the Config7 EventCode, then after `EventA_Disappear` DeviceStatus equal to the stored base and the DDS entry removed.

### 4.12 `SDCI_TC_0124` — no error-count behavior (shallow)

`check_0124` (`spec_checks.py:307-309`) reads `0x0020` and asserts `len == 2`. The spec also requires an error stimulation, count increment by one, power cycle, and reset to `0x0000`. This check would pass on a constant counter.

## 5. Additional systematic problems

- **Only `OK`/`ERR` is asserted** for 0054, 0057, 0058, 0059, 0061, 0066, 0104, 0107, 0109, 0110, 0108, 0111-0121, 0123, 0136, 0137, 0140. For negative ISDU cases the spec usually requires a specific `ErrorCode`/`AdditionalCode` (0x8011, 0x8012, 0x8023, 0x8030, 0x8033, 0x8035); these are not asserted.
- **`assert_ok` (`spec_checks.py:25-28`)** only checks that the line contains `OK` and that the reported length is below a cap. It never verifies I-Service, CHKPDU, ExtLength, UTF-8, or content.
- **Vendor hooks are not the Test Spec objects**: `0x00E1` (event injection), `0x00E6` (NVM flush), `0x00E9` (local-change trigger) are used instead of `Config7`/real local parameterization. They are useful fixtures but do not prove the application behavior specified by the case.
- **Precondition is often not established**: 0070 (PREOPERATE), 0072/0073 (interruption), 0089 (explicit communication setup), 0134 (maximum MasterCycleTime), 0378 (PREOPERATE), 0322 (DSIdle_2). `ensure_operate` always drives the fixture to OPERATE (`test_spec_all.py:117-192`).
- **8 mapped checks are not executed at all**: 0055, 0064, 0134, 0155, 0316, 0317, 0318, 0323. Their presence in `CHECKS` (`spec_checks.py:947-1020`) can be mistaken for coverage.

## 6. Test Spec IDs absent from the HIL CHECKS

The spec has 313 case blocks; 153 have an EUT containing `Device`. The HIL `CHECKS` covers 72 of those; 81 device cases are absent. Classification of the 81 absent cases (grouped by what they need):

### 6.1 Hardware / physical layer / fault-injection fixture

`0011, 0012, 0013, 0014, 0015, 0016, 0017, 0018, 0025, 0026, 0027, 0028, 0029, 0294, 0295, 0296, 0297, 0300, 0301, 0302, 0304, 0305, 0311, 0312, 0313, 0319, 0320, 0376, 0377`

These are physical-layer measurements, timing, wake-up, eye diagrams, response time, isolation, or PDOut fail-safe tests. They need an oscilloscope/PLT/fault fixture or a PDOut-only DUT; they cannot be honestly replaced by RTT ISDU commands.

### 6.2 IODD / vendor oracle

`0056, 0090, 0091, 0092, 0093, 0094, 0095, 0096, 0141, 0142, 0149, 0150, 0151, 0152, 0375` plus `CP_TC_0001..0006` and `TC_Device_Identification`

These require the device IODD and/or profile reference values: Config1/Config2 objects, VendorID/DeviceID, MinCycleTime, FunctionID, revision, PD descriptors, default values, ProfileCharacteristic, and full read/write parameter verification. Without the IODD they are blocked-oracle, not pass/fail candidates.

### 6.3 Block-parameterization / tool gate

`0081, 0082, 0083, 0084, 0143, 0144, 0145, 0146, 0147, 0148, 0324, 0325, 0326, 0327, 0328, 0329, 0330`

These need a block-parameterization master/test tool (ParamDownloadStart/Break, upload during download, etc.). Some of the state-machine logic could be unit-tested with the existing DS/ISDU mocks, but a HIL check needs the tool.

### 6.4 Could be unit-tested (protocol/state machine, no special fixture)

`0034, 0035, 0036, 0037, 0038, 0039, 0040, 0041, 0043, 0044, 0045, 0046, 0047, 0049, 0087, 0306, 0314, 0315`

STARTUP/PREOPERATE/OPERATE transitions, illegal transitions, truncated M-sequence, simulated reset, DeviceID/RID overwrite, and PD-validity event behavior are all reachable through the DLL/ISDU contexts with mock PHY and could be added to the CMocka suite. Some already have partial unit tests in `tests/conformance_traceability.csv` (0039/0040), but that is library-level evidence, not the HIL check.

### 6.5 Not applicable to this DUT (claimed)

`0085, 0086` (V1.0 compatibility/interleave). These are optional/legacy; the report marks them n/a. They should be documented as scope exclusions, not counted as conformance coverage.

## 8. Remaining uncertainty

- The HIL master firmware's `od get/set`, `page get/set`, `event *`, and vendor-hook semantics are not in this repository. The audit read the checks and the device library, not the master command parser. Byte order/length handling of the hooks could change some verdicts.
- The IODD for the DUT is not available in the audited tree. Config1/2/3/7 objects and default values are therefore unverifiable. This is why several cases are legitimately blocked-oracle, but it also means the HIL cannot prove the IODD-dependent criteria.
- The report's `n/a` claims for 0155/0316/0317/0318 and 0323 conflict with the device library source. The actual STM32 HIL build configuration (`IOLINK_FEATURE_SYSTEM_COMMAND`, DS feature) was not read. If the HIL build differs from the Linux build, the `n/a` claim may still be true; it is currently undocumented.
- The report run was not re-executed during this audit (no hardware access). All pass/fail statements are about the check code and the provided report, not a fresh HIL run.
- `pdftotext -layout` can reorder table cells across page breaks. The extracted case fields in `/tmp/cases2.json` were spot-checked against the raw text for the implemented cases; the raw PDF remains the authority.
